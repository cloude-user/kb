## KubeOps-Aegis Infrastructure Blueprint

### 1. Executive Summary: The 3-Tier Identity Model
In production AKS deployments, security and least-privilege are enforced across three distinct layers of identity:

```
                          Azure Entra ID (IAM)
                                    │
       ┌────────────────────────────┼────────────────────────────┐
       ▼                            ▼                            ▼
1. AKS Control Plane         2. Kubelet Identity          3. Workload Identity
   Identity (aks_identity)      (Worker Node VMSS)           (Pod ServiceAccount)
   [aks.tf: Line 7]             (Auto-generated)             [identity.tf: Line 7]
       │                            │                            │
       ▼                            ▼                            ▼
• Manages Azure resources    • Pulls container images    • Interacts with Azure Data
• Provisions Azure LBs       • Role: "AcrPull" on ACR      (Key Vault, Blob Storage,
• Joins VNet subnets         • Zero stored passwords        PostgreSQL)
• Talks to Azure Cloud API                               • Zero client secrets/keys
                                                         • OIDC Token Exchange
```

#### Layer 1: AKS Cluster Control Plane Identity (`azurerm_user_assigned_identity.aks_identity`)
* **Where defined**: `terraform/aks.tf` (Lines 7–14, attached at Lines 40–43).
* **Role**: Used by the Kubernetes Control Plane (API Server, Cloud Controller Manager).
* **Responsibilities**:
  - Dynamically provisions Azure Load Balancers when a service of type `LoadBalancer` is created.
  - Attaches worker VMSS NICs to `snet-aks-system` and `snet-aks-user`.
  - Manages Public IPs and routing tables inside Azure VNet.

#### Layer 2: Node Kubelet Managed Identity (`kubelet_identity`)
* **Where defined**: Automatically generated by AKS during cluster creation.
* **Role Binding**: `terraform/acr.tf` (Lines 20–25).
* **Role**: `AcrPull` on `azurerm_container_registry.acr` (`kubeopsaegisacrprd.azurecr.io`).
* **Responsibilities**:
  - Kubelet agent running on each worker VM calls Azure Entra ID to fetch an access token.
  - Seamlessly pulls private container images (`backend:v1`, `frontend:v1`, `agent:v1`) from ACR.
  - No Docker login credentials, secrets, or `imagePullSecrets` required in YAML manifests!

#### Layer 3: Workload Identity / Federated OIDC (`azurerm_federated_identity_credential`)
* **Where defined**: `terraform/identity.tf` (Lines 18–26).
* **Role Binding**: Binds Kubernetes ServiceAccount `system:serviceaccount:default:kubeops-agent-sa` to Azure Managed Identity `kubeops-aegis-prd-agent-identity`.
* **Responsibilities**:
  - When backend/AI agent pods spin up, AKS injects an OIDC projected service account token (`api://AzureADTokenExchange`).
  - Azure Entra ID validates the token against AKS's `oidc_issuer_url`.
  - The pod gains access to Azure Key Vault secrets, Blob storage containers, and PostgreSQL without storing any database passwords or Azure connection strings in application configuration!

### 2. Networking & Traffic Architecture

#### A. Ingress (Inbound Pod Traffic) vs Egress (Outbound Pod Traffic)
| Traffic Flow | Mechanism | Handled By |
| :--- | :--- | :--- |
| **Inbound (Ingress)** | Public Internet ➔ Load Balancer ➔ Ingress Controller ➔ Pod | **Azure Cloud Controller Manager** (Automatic, on-demand). No manual `azurerm_lb` in Terraform. |
| **Outbound (Egress)** | Pod ➔ Azure CNI Overlay ➔ Host Node ➔ Azure NAT Gateway ➔ Internet | **Azure NAT Gateway (`20.239.251.132`)** via `outbound_type = "userAssignedNATGateway"`. Zero SNAT port exhaustion. |

#### B. Why No `azurerm_lb` in Terraform?
* In Kubernetes, external load balancers are **declaratively requested from within the cluster**, not statically declared in Terraform.
* When Ingress NGINX or Cilium Ingress is installed via Helm/Manifests with `spec.type: LoadBalancer`, AKS talks to Azure ARM directly to provision an Azure Standard Load Balancer, health probes, and backend pools dynamically.
* If user nodes scale from 2 to 10 nodes, AKS automatically synchronizes the Load Balancer backend pool without needing a `terraform apply`.

#### C. High-Performance CNI: Azure CNI Overlay + Cilium eBPF
* `network_plugin = "azure"` + `network_plugin_mode = "overlay"`:
  - Pods get private IPs from a dedicated pod CIDR (`10.0.0.0/16`), saving precious VNet subnet IPs.
* `network_policy = "cilium"` + `network_data_plane = "cilium"`:
  - Replaces traditional, slow `iptables` with Linux **eBPF (Extended Berkeley Packet Filter)** bytecode running directly in the Linux kernel.
  - Sub-millisecond latency for inter-service communication and layer-7 API security filtering.

### 3. Node Pool Segregation: System Pool vs User Workload Pool

```
                                AKS CLUSTER
  ┌────────────────────────────────────────────────────────────────────────┐
  │                                                                        │
  │  [System Node Pool: "systempool"]                                      │
  │  • Subnet: snet-aks-system (10.100.1.0/24)                             │
  │  • Taint: CriticalAddonsOnly=true:NoSchedule                           │
  │  • Workloads: CoreDNS, Metrics Server, CSI Storage Drivers, Cilium    │
  │  • VM SKU: Standard_D2s_v5 (2 Nodes, Static)                           │
  │                                                                        │
  ├────────────────────────────────────────────────────────────────────────┤
  │                                                                        │
  │  [User Node Pool: "userpool"]                                          │
  │  • Subnet: snet-aks-user (10.100.2.0/24)                               │
  │  • Taint: None                                                         │
  │  • Workloads: Backend API, Frontend Web, AI Agent, ArgoCD, Celery      │
  │  • VM SKU: Standard_D4s_v5 (Min: 2, Desired: 3, Max: 10 Auto-scaling)  │
  │                                                                        │
  └────────────────────────────────────────────────────────────────────────┘
```
* **System Pool Isolation**: By applying `only_critical_addons_enabled = true`, customer application pods can never starve critical cluster control plane components (CoreDNS, Cilium) of CPU or memory.
* **User Pool Elasticity**: Auto-scales based on traffic spikes and processing load.

### 4. Terraform In-Cluster Providers (`kubernetes`, `helm`, `kubectl`)
Lines 104–126 of `aks.tf` provide credentials to let Terraform interact with the cluster API server:

```hcl
provider "kubernetes" {
  host                   = try(azurerm_kubernetes_cluster.aks[0].kube_config[0].host, "https://127.0.0.1:443")
  client_certificate     = try(base64decode(azurerm_kubernetes_cluster.aks[0].kube_config[0].client_certificate), "")
  client_key             = try(base64decode(azurerm_kubernetes_cluster.aks[0].kube_config[0].client_key), "")
  cluster_ca_certificate = try(base64decode(azurerm_kubernetes_cluster.aks[0].kube_config[0].cluster_ca_certificate), "")
}
```

* **`host`**: Control plane API server HTTPS URL.
* **`client_certificate` & `client_key`**: Admin mutual TLS (mTLS) cryptographic identity.
* **`cluster_ca_certificate`**: Root CA ensuring Terraform only talks to the authentic cluster.
* **`try(...)` Fallback**: Crucial for CI/CD plans before the cluster is created. Prevents `index out of bounds` errors when `count = 0`.
